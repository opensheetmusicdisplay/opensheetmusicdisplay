Thanks for pointing me to #1673. I had not seen it when I began this work. I have now rebased the draft on current `develop` and audited it against both #1673 and the VexFlow 5 concerns collected in #1139.

This is no longer presented as an alternative minimal API port. My starting problem was voice-and-piano engraving: with the VexFlow 1.2 formatter, lyric-to-note relationships, rhythmic spacing, rerenders, and slurs were poor enough that compiling against a new API while preserving the old output was not a useful endpoint. The branch therefore uses the modern formatter and follows the consequences through OSMD's old renderer assumptions. Acceptance is based on stable musical geometry and browser-rendered comparisons rather than pixel identity with VexFlow 1.2.

For #1139 specifically, I have made the former patch disposition explicit. The inactive `VexFlowPatch` archive is removed only after classifying its relevant behavior. Required behavior is now covered by small VexFlow review units or focused OSMD code/tests: positioned articulations (#322), formatter padding (#324), finalized notation geometry (#325), tuplet rerender stability (#326), and grace/slur geometry (#327). The draft is temporarily pinned to immutable, clean-install-verified integration commit `e9ae567e1e25d75075d8c4fae4fd8119cd6b0b08`; it must use an official VexFlow release before merge.

The font contract is also explicit. OSMD imports VexFlow through one internal adapter and deliberately selects the fontless engine there. The normal OSMD bundle is nevertheless self-contained: it embeds and awaits full Bravura, subsetted Bravura Text, and Academico regular/italic/bold before any score measurement. A separately named core bundle contains no font payload and requires the host to provide the same typed profile. Standalone SVG exports embed the active profile by default, with an opt-out. The exact font files, hashes, subset code points, and OFL texts are included.

The broader renderer changes cover the generic spacing, lyric, rest, barline, repeat, volta, tie, slur, articulation, dynamics, and harmony assumptions exposed by the port. Dorico was used as one visual reference, but no imported Dorico geometry is relied upon and the code/commit language is renderer-neutral.

I have retained structured annotation diagnostics and a bundle-to-bundle browser comparison workflow. This allows the old draft, another VexFlow 5 branch, and the current result to be rendered side by side without retaining a legacy production layout engine. Automated failures are limited to objective faults such as load errors, missing SVG, non-finite geometry, required-font failure, and first/second-render drift; aesthetic warnings remain visible for review. The PR's Validation section gives the exact standalone OSMD commands and the generated `index.html` path for reviewing the complete annotated OSMD corpus.

The PR contains a patch-disposition ledger and a reproducible range-diff command. Validation now covers the focused #1139 regression matrix, fresh-browser bundled/core font checks, portable offline SVG verification, and the complete OSMD corpus render. I am happy to split the harmony presentation policy from the migration if that makes review easier.
